# 故障推送多渠道：公众号 + 邮箱并行

- **日期**: 2026-06-03
- **模块**: device-mgmt · `customers.html`、`staff-management.html`、`faults.html`
- **基线**: `origin/main` 当前 HEAD
- **分支**: 建议新开 `feat/fault-push-channels`

## 背景

当前故障推送链路是单一邮箱：
- 商户档案有一个「故障通知邮箱」字段（见 `customers.html` 表单与列表渲染）。
- 故障列表 `faults.html` 通过「设备 → 所属商户 → 故障通知邮箱」三步查出收件邮箱，渲染成「✉️ 推送至 xxx」徽章。

业务侧需要把渠道扩展到「微信公众号」，并把「公众号 ID 跟着人员走」「渠道开关跟着商户走」这两个分工固化下来。

## 目标

- 商户可以并行选择「邮箱推送」「公众号推送」两个渠道，也可以都不选（即本商户不接收故障推送）。
- 公众号渠道下，推送对象由「商户旗下、拥有故障接收权限、且登记了公众号 ID 的员工」自动聚合，运营无需在商户那侧重复维护接收人名单。
- 任何会让「勾选的渠道实际无人能收」的配置变更都会被系统拦截或自动修正，不允许出现「勾了却发不出去」的状态。
- 故障列表能一眼看出每条故障会经由哪些渠道送达。

## 不在范围

- 真实的微信公众号对接、模板消息接口调用（项目目前是静态原型，本期只到 UI、数据模型、本地校验为止）。
- 邮件发送通道本身的实现（同上）。
- 商户自助端登录入口（公众号 ID 仍由运营在「人员管理」代员工配置，不新增商户自助门户）。
- 历史故障的回溯通知（仅影响生成时间晚于本期上线的新故障的徽章呈现）。

## 名词约定

- **商户**：`customersData` 里的一条客户记录，对应一家咖啡店牌子或加盟主体。
- **员工**：`staffManagersData` 里的一条人员记录，归属于某个商户。
- **故障接收权限**：员工权限中的「能查看故障」一项（即当前权限体系中的故障模块查看权限）。
- **接收范围**：员工在「故障」模块上的可见设备范围（沿用现有 `moduleDeviceScopes.faults`），决定具体哪些设备的故障真正推给该员工。
- **公众号 ID**（= 公众号 OpenID）：员工本人在咖啡运营公众号下的不透明用户标识，由运营录入，本期按纯文本保存。后文 UI 字段标签写作「公众号 OpenID」、业务规则段落写作「公众号 ID」，两者指同一字段。
- **可达接收人**：某商户下，同时满足「拥有故障接收权限」且「已登记公众号 ID」的员工集合。注意：本期可达性判定**只看权限与 ID**，不再叠加「接收范围」——「接收范围」只在故障实际发生时决定具体推给名单中的哪几位（即同一商户下不同员工可能各自只收到自己范围内设备的故障），不影响商户层面「能不能开公众号渠道」的判定。
- **推送渠道**：本期定义两种取值——「邮箱」「公众号」。

## 设计

### 1. 数据模型变更

**商户记录**新增一个字段，用于表达推送渠道的勾选状态：

- 推送渠道列表：可同时包含「邮箱」「公众号」两个值，也可以为空数组。
- 原有的「故障通知邮箱」字段保持不变。

**员工记录**新增一个字段：

- 公众号 ID：纯文本，空串表示未登记，最大长度 128。

**默认值与回填**：

- 商户读取时若未带「推送渠道列表」字段：当原邮箱字段非空时回填为「[邮箱]」，否则回填为「[]」。保证存量商户行为不变（原本配了邮箱的继续按邮箱走）。
- 员工读取时若未带「公众号 ID」字段：回填为空串。
- 回填发生在加载阶段，沿用现有的 `bootstrapStaffManagers` / 客户加载模式，按需写回 localStorage。

### 2. 商户管理 UI 改造（`customers.html`）

表单里把「故障通知邮箱」一行扩成两行：

```
故障推送渠道   [ ] 邮箱推送   [ ] 公众号推送
故障通知邮箱   [_____________________________]
```

- 两个渠道是独立复选框，可以同时勾选，也可以都不勾。
- 「故障通知邮箱」输入框的可用/必填状态跟随「邮箱推送」复选框：勾选时输入框启用且必填；未勾选时置灰且清空校验。
- 「公众号推送」复选框旁边给一句辅助说明：「接收人将自动从本商户旗下『拥有故障接收权限并登记了公众号 ID』的员工中聚合」。

**新建商户场景下的特殊处理**：商户尚未关联任何员工时，「公众号推送」复选框置灰，附上 tooltip 提示「请先到『人员管理』为本商户添加登记了公众号 ID 的员工，再回此处勾选」。这避免新建路径被卡。

**列表/资料展示侧**（参见现有的资料卡片与客户列表渲染）：把原本只显示邮箱的位置扩成最多两个并列徽章，「✉️ 邮箱推送 · xxx」「📱 公众号推送」按勾选状态分别呈现，都未勾时显示「🔕 未配置推送」。

### 3. 人员管理 UI 改造（`staff-management.html`）

在员工新增/编辑弹窗的「基础信息」区域、紧跟「手机号」之后新增一行：

```
公众号 OpenID  [_____________________________]
                ℹ️ 配置后，当所属商户开启「公众号推送」时，本人将接收授权范围内的故障消息
```

- 字段非必填，按文本保存，仅做 `trim` 与长度上限校验，不做格式正则（OpenID 是微信侧分配的不透明字符串）。
- 员工列表行末尾追加一个轻量状态徽章：已登记 → 灰底「📱 已绑公众号」；未登记不显示徽章，避免噪声。

### 4. 故障列表展示（`faults.html`）

把原 `getFaultNotifyEmailForDevice` 单值取邮箱的逻辑，重构为先取「该设备所属商户的推送渠道列表」，再按渠道渲染对应徽章：

| 商户的推送渠道勾选 | 故障行徽章 |
|---|---|
| 仅勾「邮箱推送」 | `✉️ 邮箱推送` |
| 仅勾「公众号推送」 | `📱 公众号推送` |
| 都勾 | `✉️ 邮箱推送` `📱 公众号推送`（并排） |
| 都不勾 | `🔕 未配置推送`（灰色） |
| 第 6 节自愈处理过 | 渠道徽章右上角追加橙色小角标，hover 看自动修正历史 |

徽章不展示具体邮箱地址，也不列出公众号接收人姓名 —— 这些落在商户详情和员工列表里查看，避免列表行过长。

### 5. 公众号推送的接收人保护规则（PRD 段落）

> 本节为业务规则陈述，可直接进入产品 PRD。

为了避免出现「商户在系统里勾了用公众号接收故障，但实际没人收得到」的尴尬情况，对配置变化做以下保护。

**核心原则**：商户可以选择不接收任何故障推送；但只要勾了某个渠道，这个渠道必须有人能真正收到。

#### 5.1 配置时的把关

- 商户可以同时勾选「邮箱」和「公众号」两个渠道，也可以一个都不勾（=本商户不接收推送，系统允许）。
- 勾了「邮箱」，就必须填一个合法的故障通知邮箱。
- 勾了「公众号」，就必须确保该商户旗下至少有一位「能查看故障的员工」已经登记了自己的公众号 ID。否则系统不让保存，并提示运营人员先去补员工的公众号 ID。
- 新建一个商户时，因为还没有任何员工，公众号这个勾选框默认置灰、暂时不可用。等到运营人员先在「人员管理」给本商户添加了能查看故障且登记了公众号 ID 的员工之后，再回到商户页面，这个勾选框就会自动可用。

#### 5.2 员工那边发生变化时的保护

员工是「公众号能不能收到故障」的实际接收人，所以员工资料的变化会反向影响商户的推送配置。以下情况都属于「会让某个商户的公众号渠道失去全部接收人」：

1. 员工的公众号 ID 被清空；
2. 员工的账号被停用；
3. 员工被取消了故障查看的权限；
4. 员工被转到了别的商户；
5. 员工被删除。

只要运营人员准备提交以上任何一种变更，系统会先做一次「预演影响」检查：如果发现这个动作会让某个商户的公众号推送从此没人能收到，就会弹出一个确认窗口，给出三个选择：

- **推荐：保留员工的这次变更，并自动取消该商户的「公众号推送」勾选**（变成只剩邮箱推送，或者完全不推送）；
- 暂不保存，先去人员管理给该商户补一位新的公众号接收人；
- 取消本次操作。

运营人员选了「自动取消」后，该商户的列表会出现一个临时的提示气泡「公众号渠道已自动取消，因 XX 员工变动」，方便事后追溯。

#### 5.3 打开页面时的自动校对

考虑到数据可能在两个页面之间出现短暂不一致，或者被外部直接改坏，每次打开「商户管理」和「故障列表」时，系统都会自动做一次轻量校对：

- 凡是发现某个商户「勾了公众号渠道但实际没有可达接收人」，系统会自动把公众号渠道的勾选取消掉，并在该商户的列表行上挂一个「⚠️ 配置已自动修正」的提示，hover 可以看到原因和发生时间。
- 这一类自动修正以及 5.2 中的运营确认型取消，统一会留存最近的若干条记录，运营人员可以在「商户管理」页顶部的提示入口查看历史，确保渠道不会「悄悄掉了」无人知晓。

#### 5.4 故障列表上呈现给运营的样子

- 商户勾了邮箱 → 故障行显示「✉️ 邮箱推送」徽章；
- 商户勾了公众号 → 故障行显示「📱 公众号推送」徽章；
- 两个都勾 → 两个徽章都显示；
- 都没勾 → 故障行显示「🔕 未配置推送」灰色徽章，表示这条故障合法地无人接收；
- 自愈发生过的商户，徽章上多一个橙色小角标，hover 看到自动修正历史。

### 6. 数据自愈与历史记录的实现锚点

- 在 `customers.html` 与 `faults.html` 的初始化阶段（与现有 `bootstrap*` 同位）增加 `reconcileNotifyChannels()`：遍历商户，凡发现「勾了公众号但无可达接收人」就把该渠道剥离，写一条记录到 `localStorage` 键 `faultNotifyReconciliationLog`（环形队列，保留最近 20 条）。
- 5.2 中的运营确认型取消复用同一日志键，事件类型字段区分「自动校对」与「运营确认」。
- 「商户管理」页顶部增加一个轻量入口（铃铛或一行小字「最近 N 条推送配置自动调整」），点开后侧滑展示该日志，按时间倒序，每条包含：商户名、事件类型、触发原因、时间。日志可一键清空。

## 风险与权衡

- **自动取消渠道可能让运营「不知道渠道掉了」**：通过 5.3 的日志入口 + 商户行的临时提示气泡缓解；如果运营仍然忽略，最差情况是故障继续以「邮箱推送」单通道送达或「未配置推送」（不会出现假装在推但其实推不出去）。
- **OpenID 校验仅做长度/裁剪，不做格式正则**：微信侧 OpenID 形态可能演化，过严校验更容易误伤；本期按文本存，等真正对接公众号 API 时再加格式校验。
- **公众号渠道下接收人是聚合算出来的**：意味着「员工权限变更」「员工设备范围变更」会即时影响接收人。这是有意为之，避免运营需要在两处维护同一份接收人名单；副作用是员工侧的修改要经过 5.2 的预演检查。
